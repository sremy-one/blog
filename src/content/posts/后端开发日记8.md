订单状态改变以后，用户既需要在消息中心看到记录，也希望收到微信订阅消息。两种渠道作用不同：站内消息保存业务事实，微信消息负责把用户从应用外叫回来。

## 1. 站内消息按当前用户隔离

用户消息列表接口仍然使用通用分页结构，但查询条件由 Service 补充：

```java
HyNotification query = request == null
        ? new HyNotification() : request;
query.setWxUserId(SecurityUtils.getUserId());
return notificationMapper.selectHyNotificationList(query);
```

前端可以筛选已读状态或通知类型，却不能查询其他用户 ID。把身份条件放在 Service 中，可以防止 Controller 新增入口时忘记隔离。

## 2. 为什么要记录订阅额度

微信一次性订阅消息需要用户主动允许。前端获得授权结果后，把模板 ID 和允许次数上报后端，后端按“用户 + 模板”保存可用额度。

额度记录至少包含：

- `availableCount`：还可发送多少次；
- `consumedCount`：已经使用多少次；
- 用户 ID 与模板 ID 联合定位一条记录。

同一模板再次授权时增加额度，而不是覆盖已有计数。

## 3. 发送前预扣

如果先调用微信、成功后再减额度，两个并发发送都可能看到余额为 1，最后发送两次。项目把顺序改为：

```text
原子扣减 availableCount
  -> 调用微信订阅消息接口
  -> 成功：保留 consumedCount
  -> 失败：恢复刚才预扣的额度
```

Mapper 的 `consumeAvailableCount` 在 SQL 条件中要求可用数大于 0，并同时完成减一与已用数加一。是否扣减成功由受影响行数判断。

## 4. 失败恢复不是无限重试

网络异常或微信响应失败时，服务恢复额度，并记录发送失败结果。恢复解决的是“用户授权不能被白白消耗”，不代表应该在当前请求里无限重试。

对于明确的 Token 失效，可以刷新 Token 后重试一次；对于模板参数错误、用户拒收等业务错误，应保留失败状态供排查。

## 5. 双通道如何协作

订单审核、开始飞行、送达或异常处理完成时，业务 Service 可以先写站内通知，再尝试发送微信订阅消息：

| 通道 | 特点 | 失败后的处理 |
| --- | --- | --- |
| 站内消息 | 可查询、可分页、可保留历史 | 属于业务数据，应随事务处理 |
| 微信订阅消息 | 到达应用外、依赖用户授权和第三方平台 | 记录结果并恢复额度，不应破坏已完成业务 |

是否让外部推送失败回滚订单，需要按业务风险决定。通常订单状态是主事实，推送失败应进入补偿或重试，而不是把已经完成的配送改回原状态。

## 6. 本篇小结

消息系统不能只关注“发送接口返回成功”。站内消息负责可追溯，订阅额度负责发送资格，原子预扣负责并发正确性，失败恢复负责不浪费授权。把这些角色分开，通知链路才具备可解释的失败处理。
