管理端基于若依前端结构继续开发，页面看起来是熟悉的侧边栏、顶部导航和内容区，但真正新增业务页面时，路由是否挂在 `Layout` 下、详情页是否保持菜单高亮、返回后列表是否刷新，都会直接影响使用体验。

## 1. 管理端技术结构

| 技术 | 作用 |
| --- | --- |
| Vue 3 | 页面和组件开发 |
| Element Plus | 表格、表单、弹窗、标签等基础组件 |
| Pinia | 全局状态管理 |
| Vue Router | 菜单页、详情页和隐藏路由 |
| Axios | 管理端接口请求 |
| ECharts | 报表与数据可视化 |

业务页面主要位于：

```text
src/views/manage
├── delivery-order
├── delivery-order-history
├── delivery-proof
├── exception-ticket
├── flight-task
├── notification
├── report-snapshot
├── transfer-point
└── wx-user
```

## 2. 列表页与详情页的关系

订单列表负责筛选和定位订单，详情页负责展示地图、订单信息、流程日志和操作按钮。

```text
订单列表
  ↓ 点击订单号/查看
订单详情
  ├── 地图与航线
  ├── 订单信息
  ├── 配送凭证
  ├── 操作流程
  └── 审核、飞行、送达等操作
```

订单详情不是侧边栏中的独立菜单，所以使用隐藏路由：

```js
{
  path: '/manage/delivery-order/detail',
  component: Layout,
  hidden: true,
  children: [
    {
      path: ':orderId(\\d+)',
      component: () => import('@/views/manage/delivery-order/detail'),
      name: 'DeliveryOrderDetail',
      meta: {
        title: '订单详情',
        activeMenu: '/manage/delivery-order'
      }
    }
  ]
}
```

这里有两个关键点：

1. 父级组件必须是 `Layout`，这样详情页仍在管理端整体框架内；
2. `activeMenu` 指向订单列表，进入详情后侧边栏仍高亮“订单中心”。

## 3. 页面层级与交互形式

管理端同时存在列表页、详情页和操作弹窗。页面复杂度决定了它应该处于哪一层：

| 交互 | 适合形式 |
| --- | --- |
| 临时确认、少量字段编辑 | Dialog |
| 信息复杂、需要地图和多标签 | 独立路由页面 |

订单审核、开始飞行和确认送达都属于围绕当前订单的短操作，因此拆成 Dialog；订单详情、异常处理详情包含完整业务上下文，因此使用独立页面。

页面跳转统一进入挂载在 `Layout` 下的业务路由：

```js
router.push(`/manage/delivery-order/detail/${orderId}`)
```

这样顶部导航、侧边栏、面包屑和标签页始终属于同一套管理端框架。

## 4. 组件拆分

订单业务中把不同操作拆成独立组件：

```text
DeliveryOrder/
├── ApproveOrderDialog.vue
├── RejectOrderDialog.vue
├── StartFlightDialog.vue
├── DeliveryFailedDialog.vue
└── ConfirmDeliveredDialog.vue
```

详情页只负责判断当前状态应该显示哪些操作，具体表单校验和提交逻辑交给对应组件。

这种拆分避免详情页继续长成“什么都能做、谁也不敢动”的超级组件。

## 5. 页面上下文

详情页返回列表时，使用路由历史可以保留用户之前的筛选上下文：

```js
function handleBack() {
  router.back()
}
```

如果是从异常处置进入子订单详情，同样可以返回原来的异常处理页。相比写死跳转路径，历史返回更符合多入口页面的实际情况。

## 6. 本篇总结

管理端的页面骨架并不只是视觉框架，它还决定了权限、菜单高亮、面包屑和返回路径。路由配置写对了，用户感觉不到它的存在；写错了，顶部导航和侧边栏会一起“离家出走”。


`这次最大的感受是：能打开页面只是第一步，页面还得知道自己从哪里来、属于哪个菜单、准备回哪里去。`
