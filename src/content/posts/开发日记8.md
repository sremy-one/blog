小程序提供快递配送和外卖配送两种服务。它们最终都会变成平台配送订单，但用户填写的信息并不相同，因此项目保留两套表单，并复用船舶收货信息、地址选择和图片上传能力。

## 1. 两种服务的差异

| 内容 | 快递配送 | 外卖配送 |
| --- | --- | --- |
| 来源信息 | 快递公司、快递单号 | 外卖平台、外卖订单号 |
| 货物信息 | 重量、体积、备注 | 预计到达时间、骑手电话、备注 |
| 图片 | 订单截图、货物图片 | 订单截图、取货凭证 |
| 共同信息 | 船名、MMSI、收货人、手机号、收货位置 | 船名、MMSI、收货人、手机号、收货位置 |

## 2. 表单页面

```text
pages/order/courier-form.vue
pages/order/takeaway-form.vue
```

两个页面都可以：

- 新建订单；
- 编辑未支付订单；
- 修改审核退回订单；
- 从地址簿选择船舶收货信息；
- 上传订单相关图片。

## 3. 船舶收货信息

船舶收货信息单独维护在地址簿中：

```js
{
  vesselName,
  mmsi,
  receiverName,
  receiverPhone,
  regionId,
  fullAreaName,
  detailedAddress,
  longitude,
  latitude
}
```

用户选择地址后，订单 store 和 recipient store 共同填充表单。这样同一艘船的信息可以多次复用，不必每次重新输入。

## 4. 表单标准化

前端提交前先统一处理文本、数字和地址字段：

```js
const payload = normalizeOrderPayload(data)
assertValidation(validateOrderPayload(payload))
```

标准化与校验分开：

| 阶段 | 任务 |
| --- | --- |
| normalize | 去除空格、转换数字、整理地址字段 |
| validate | 检查必填项、手机号、订单号、经纬度 |

这样接口层拿到的是结构稳定的数据。

## 5. 创建与编辑

创建订单时调用：

```text
POST /manage/user/delivery-order
```

普通编辑调用更新接口；审核退回后重新提交则使用：

```text
POST /manage/user/delivery-order/{orderId}/resubmit
```

重新提交会保留订单历史，并让原订单重新进入待审核状态。

## 6. 图片上传顺序

订单创建成功后，接口返回 `orderId`，页面再上传图片凭证：

```text
校验表单
  ↓
创建或更新订单
  ↓ 获取 orderId
上传订单截图与货物图片
  ↓
进入订单详情或支付流程
```

图片上传需要依赖订单 ID，因此不能比订单创建更早执行。

## 7. 服务范围与位置

用户选择船舶位置时，需要同时考虑当前位置、地图选点和运营服务范围。位置数据最终统一成经纬度，并在订单详情和飞行任务中继续使用。

```text
用户选点 -> 经纬度 -> 服务范围校验 -> 保存船舶地址 -> 创建订单
```

## 8. 表单交互

移动端键盘会显著压缩可视区域，因此页面需要处理：

- 输入框滚动到可见位置；
- 底部按钮避让安全区与键盘；
- 下拉选择器不被遮挡；
- 图片上传后保持表单位置稳定。

## 9. 本篇总结

两套表单让我体会到，复用不一定意味着强行合并成一个大组件。共享数据模型和工具函数，同时保留各自清晰的业务字段，也是一种更稳妥的复用。
