正常订单沿固定路径前进，异常工单则要决定“原订单接下来怎么办”。项目把用户反馈和管理端处置拆开：用户只描述问题，管理端根据实际情况选择关闭、取消退款或生成重派单。

## 1. 用户提交异常反馈

提交接口接收订单 ID、异常类型和描述。Service 首先校验参数，再检查订单确实属于当前微信用户：

```java
Long wxUserId = SecurityUtils.getUserId();
HyDeliveryOrder order = orderMapper.selectById(dto.getOrderId());
checkUserOrderOwner(order, wxUserId);
```

创建人类型、创建人 ID、异常来源、初始严重程度和处理状态全部由后端补充，不能由前端决定。

## 2. 异常单号表达业务来源

异常单号按类型使用不同前缀：取消类使用 `QX`，补发类使用 `BF`，普通差错使用 `CP`，后面拼接日期和四位流水号。

单号不仅用于展示，也方便客服看到编号时快速判断大类。不过单号前缀不能代替数据库里的 `exceptionType`，机器判断仍应使用稳定枚举字段。

## 3. 三种处置不能强行合并

### 直接关闭

适用于无需改变订单和资金的情况。后端把工单设为 `CLOSED`，记录关闭结果、处理人和关闭时间，并向原订单追加一条异常处理日志。

### 取消退款

这是一个跨表动作：

```text
新增退款方向的支付记录
  -> 原订单改为 CANCELED
  -> 工单改为 COMPLETED
  -> 记录 REFUND 过程日志
```

退款金额默认取订单配送费，也允许管理端传入实际金额。支付方向、渠道、状态和退款原因分别保存，不能只在备注里写“已退款”。

### 生成重派单

重派不是修改原订单，而是复制配送所需字段生成新订单，并通过 `parentOrderId` 关联原订单。新订单直接进入 `WAIT_DISPATCH`，工单记录 `resultOrderId`，原订单与新订单各写一条过程日志。

## 4. 防止重复处置

工单处于 `COMPLETED` 或 `CLOSED` 后不允许再次处理。生成重派单前还要检查 `resultOrderId`，避免重复点击创建多个子订单。

这些判断必须发生在事务内。单纯依靠前端 loading 或按钮禁用，无法阻止两个并发请求同时到达服务器。

## 5. 事务为什么重要

退款和重派都会同时修改多张表。任意一步失败都应该整体回滚：

```java
@Transactional(rollbackFor = Exception.class)
public HyExceptionTicket refundCancel(...) {
    // 支付记录、订单、工单、过程日志
}
```

如果没有事务，可能出现退款记录已生成但订单仍在配送，或者子订单已创建但工单没有关联结果。这样的数据比接口报错更难处理，因为每张表单独看都像是有效记录。

## 6. 原订单、工单和结果订单

异常链路最终形成三个角色：

| 记录 | 回答的问题 |
| --- | --- |
| 原订单 | 哪次配送发生了问题 |
| 异常工单 | 问题是什么、由谁处理、处理结果如何 |
| 结果订单 | 是否产生了重派或补发任务 |

关系字段比把所有信息塞进一张超长备注更适合查询和统计，也方便前端从异常详情跳转到原订单与重派单。

## 7. 本篇小结

异常处理的核心不是“改成已处理”，而是把处理结果真正落到订单、资金和新配送链路上。明确三种动作、建立父子关系、增加防重复校验并使用事务，才能让异常闭环可追溯。
