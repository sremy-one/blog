订单中心是管理端最像“交通指挥台”的模块。列表里每一行看起来都很安静，但背后可能正在等待审核、等待飞行、配送途中，或者已经因为天气和设备问题进入异常处理。

## 1. 订单列表

订单列表提供平台订单号、船舶名称、订单状态等查询条件，并通过分页接口获取数据。

```js
const queryParams = reactive({
  pageNum: 1,
  pageSize: 10,
  orderNo: undefined,
  vesselName: undefined,
  orderStatus: undefined,
  orderByColumn: 'createTime',
  isAsc: 'desc'
})
```

列表中的订单号不是普通文本，而是详情入口：

```html
<el-link type="primary" @click="handleDetail(scope.row)">
  {{ scope.row.orderNo }}
</el-link>
```

订单号用于业务展示，`orderId` 用于接口查询和路由跳转。这两个字段必须从一开始就分清楚。

## 2. 订单详情布局

详情页采用左右布局：

| 区域 | 内容 |
| --- | --- |
| 左侧地图 | 起飞点、收货点、航线、配送结果 |
| 右侧信息 | 订单信息、操作流程、凭证、状态操作 |

订单信息包括平台订单号、原单号、服务类型、来源渠道、船舶信息、包裹信息和图片凭证。操作流程则通过时间线展示订单状态变化。

```html
<el-tab-pane label="操作流程" name="flow">
  <OrderProcessTimeline :logs="processLogs" />
</el-tab-pane>
```

## 3. 状态决定操作

页面不会让所有按钮一直出现，而是根据订单状态展示对应动作：

```text
待审核     -> 审核通过 / 审核退回
待配送     -> 取消订单 / 开始飞行
配送中     -> 配送失败 / 确认送达
已完成     -> 查看流程与凭证
```

模板中将操作区域分组：

```html
<div v-if="showAuditButtons">
  <el-button type="danger">审核退回</el-button>
  <el-button type="primary">审核通过</el-button>
</div>
<div v-else-if="showFlightButtons">
  <el-button type="danger">取消订单</el-button>
  <el-button type="primary">开始飞行</el-button>
</div>
```

这样不仅减少误操作，也让页面直接反映当前业务阶段。

## 4. 审核退回与重新提交

审核退回不能只修改一个状态，还要记录退回原因和说明。小程序用户修改订单后重新提交，管理端需要识别这是一次重新审核，而不是全新的订单。

审核确认文案也会根据历史状态变化：

```js
if (isResubmittedOrder) {
  return `订单${orderNo}为审核退回后重新提交，确认人工复核无误并审核通过？`
}
```

这类文案看似只是提示，实际上帮助运营人员判断操作上下文。

## 5. 开始飞行

订单进入待配送后，飞手或运营人员登记飞行信息。确认开始飞行后：

1. 订单状态变为配送中；
2. 生成或关联飞行任务；
3. 写入订单流程日志；
4. 小程序端可以进入查看位置页面；
5. 消息中心接收订单动态。

## 6. 确认送达

确认送达需要同时处理业务状态和配送凭证：

- 填写送达说明；
- 上传送达图片；
- 更新订单状态；
- 记录完成时间；
- 在小程序端开放查看回单入口。

图片展示没有直接把鉴权地址交给 `<img>`，而是通过 `AuthenticatedImage` 组件加载，避免私有图片因缺少 token 而显示失败。

## 7. 配送失败

配送失败并不是简单结束订单，而是异常流程的入口。失败弹窗会登记：

| 字段 | 作用 |
| --- | --- |
| 失败原因 | 说明本次配送为什么中止 |
| 飞行处理结果 | 记录无人机或任务处理情况 |
| 异常类型 | 决定后续进入重派还是其他处理 |
| 失败说明 | 给后续处理人员补充上下文 |

提交后，订单中心与异常处置模块开始联动。

## 8. 本篇总结

订单中心让我认识到，状态按钮不是几个接口的集合，而是一套受到当前状态、权限和历史操作共同约束的流程。
